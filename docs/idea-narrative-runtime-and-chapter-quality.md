# Idea：Narrative Runtime 与 Chapter Quality Control 的双层架构

## 背景

当前仓库对多 Agent 协作小说生产的讨论，已经逐步形成两个相互关联、但不应混为一谈的控制层：

1. **系统层控制**：维护叙事状态、真值、资源、章节推进与返工路由。
2. **章节层控制**：维护单章内的阅读体验、沉浸感、节奏变化、段落黏性与文本自然度。

前者更像游戏中的剧情状态管理器 / 任务状态机；后者更像小说导演系统 / 编辑部的章节打磨流程。

这个区分解释了为什么系统可以“很稳”，文本却仍可能“像剧本、像摘要、像执行记录”。

---

## 1. 两个核心问题域

### 1.1 Narrative System：负责“故事不崩，能持续推进”

适合通过状态文件、规则检查、Agent 分工来维护：

- 时间线
- 势力与关系状态
- 已公开 / 未公开信息
- 角色目标、情绪、知识边界
- 悬念、伏笔、暴露风险等叙事资源
- 章节推进、返工、重规划

它回答的问题是：

> 这章应该发生什么？哪些不能发生？哪些资源被推进或消耗？

### 1.2 Prose Quality：负责“这一章读起来像不像小说”

适合通过章节导演、扩写、章节级审稿来维护：

- 描写密度
- 情绪渗透
- POV 粘性
- 身体感受与环境锚点
- 节奏快慢与段落变化
- Scene 与 Scene 的过渡和黏合
- AI 味 / 剧本感 / 摘要感控制

它回答的问题是：

> 这章应该怎么写，读起来才有沉浸感、余味和小说感？

---

## 2. 为什么需要双层架构

很多长篇项目都会在以下两种失败模式之间摇摆：

- **系统很稳，但文本很空**：剧情能推进，状态不崩，但像在看梗概或分镜。
- **文本偶尔很好，但系统一塌糊涂**：段落有感染力，但人物失忆、设定冲突、伏笔失控。

因此更合理的目标不是让单一 Agent 同时解决所有问题，而是明确区分：

- **Narrative Runtime** 负责“正确推进”
- **Chapter Quality Control** 负责“好好讲述”

---

## 3. 题材差异：哪些更依赖系统层，哪些更依赖章节层

### 3.1 强系统依赖题材

以下题材更依赖显式状态管理、资源结算与长线控制：

- 仙侠
- 中世纪 / 架空世界构建型
- 种田流 / 经营流
- 系统流 / 升级流
- 无限流 / 副本流
- 大世界群像权谋

这些题材中，Narrative Runtime 几乎是 essential。

### 3.2 弱系统依赖但强表达依赖题材

以下题材通常不需要非常重的“数值化叙事资源管理”，但非常依赖章节表达层：

- 恋爱
- 家族兴衰
- 时代现象刻画
- 成长小说
- 社会切片 / 现实流
- 偏情绪与关系驱动的作品

这些题材依然需要 continuity，但更关键的是：

- 语气是否稳定
- 情绪是否渗透
- 场景是否沉浸
- 人物互动是否细密
- 章节是否有余味

### 3.3 两者的共同底盘

无论题材如何，最终都需要处理同一个问题：

> **章节内的文本质量控制。**

因此，双层架构不是“二选一”，而是：

- 不同题材对系统层依赖程度不同
- 但章节质量层几乎是通用基础设施

---

## 3.4 实操反馈带来的四个补强点

除了双层架构本身，实操审核还暴露出四类经常被忽略、但会直接影响章节质量的素材层缺口：

### A. Intake 太薄：只有情节，没有阅读体验目标

仅靠情节大纲不足以支持恋爱、家族、时代切片等题材。更稳妥的 intake 应至少补充：

- 本卷 / 本章希望读者获得的主情绪
- 哪些点应该让读者笑、心酸、紧张、想截图发弹幕
- 哪些场景属于传播记忆点，而不只是剧情功能点

但这层信息工作量很大，不宜在项目启动时一次性铺满。更务实的做法是：

- 在 intake 阶段只先确认卷级 / 章级体验目标；
- 等拿到章节表（chapter table）后，再逐章补命中点；
- 段落级实现交给 Chapter Director 和 Writer。

这意味着问题 1 与问题 4 确实存在部分重叠：前者负责“收集目标”，后者负责“落实到章节情感曲线”。

### B. Canon Bible 缺氛围细节：Writer 没有可复用的感官底稿

世界观规则不足以支撑章节质感。Canon Bible 还应为核心高频场景维护基础感官锚点，例如：

- 酒吧的隔音效果
- 后巷飘来的味道
- 直播间灯光打在脸上的温度感
- 某种空间给角色带来的身体反应

这里不建议穷举所有地点，而是只维护**高频场景的基础描写库**。章节里具体怎么融情于景，仍然要由当章情绪目标决定。

### C. 角色卡缺内心语法：标签足够，但语气和思维回路不够

角色的“背景 + 性格”只能防止 OOC，却不能稳定产出像同一个人写出来的内心戏。更实用的补充方式是给主要角色建立“内心语法”档案，例如用 7 个问答题固定：

- 压力大时独白怎么绕
- 撒谎或掩饰时语言怎么变
- 心动时是先否认、先自嘲，还是先合理化
- 受伤时更容易看见什么细节
- 情绪紧张时句子会变短还是变密

这类素材对恋爱文、关系流、第一 / 近距离三人称叙事尤其关键。

### D. Arc / Chapter Outline 缺情感曲线：只有事件，不足以指导表现层

章纲若只写“发生什么”，Writer 仍会倾向于把章节写成流程记录。更理想的章纲应额外说明：

- 情绪起点
- 情绪拉升或误判的中段位置
- 高潮点
- 收尾时的情感余额

考虑到维护成本，这一层不一定要人工逐章精写。更合适的做法是让 Planner / Director **自组织产出初版**，再由 Critic 或人工审核做 **自我审核**。

## 4. 推荐抽象：Novel Runtime / Narrative State Engine

如果从游戏系统设计语言理解，本项目可以被重新命名为：

> **一个以小说为输出的、由 LLM 驱动的剧情状态管理器 + 内容调度器。**

或者进一步抽象为：

- **Novel Runtime**
- **Narrative State Engine**

这个命名的价值在于：

- 它把重点从“让 AI 会写”转移到“让系统维护叙事状态并驱动写作”
- 它更适合承载 source of truth、runtime state、resource checks、replan triggers 等工程概念
- 它更贴近长期生产型小说系统，而不是一次性 prompt 写作

---

## 5. 推荐三层结构

在现有 v0.2 架构基础上，建议把系统明确拆成三层：

```text
Layer 1: Narrative Engine
  - truth_files
  - runtime state
  - resource tracking
  - planner / continuity checker / archivist

Layer 2: Chapter Director
  - chapter experience goal
  - scene weight map
  - prose tactics
  - rhythm plan
  - forbidden moves

Layer 3: Writer System
  - scene skeleton
  - scene expansion
  - optional polish
```

### 5.1 Layer 1：Narrative Engine

负责“故事正确性”：

- 状态更新
- 角色一致性
- 资源结算
- 信息边界
- 返工路由
- 重规划触发

### 5.2 Layer 2：Chapter Director

负责“表现结构”，把“发生什么”翻译成“该怎么写”：

- 哪些地方要慢下来
- 哪些地方要写环境 / 身体 / 留白
- 哪些地方不能直说
- 结尾应该留下什么样的余味或钩子

### 5.3 Layer 3：Writer System

负责具体文本生成，但不再一轮写完，而是分阶段：

1. `skeleton`：先完成 scene 功能与结构骨架。
2. `expansion`：补环境、动作、内心、节奏与段落呼吸。
3. `polish`：可选的去 AI 味、去重复、统一语气。

---

## 5.4 三种补充文档：系统层之外的表达素材层

为了让 Chapter Director 和 Writer 不再只靠临场发挥，建议在 state / truth files 之外，再维护三种“表达素材层”文档：

1. **experience brief / richer intake**：记录卷级、章级体验目标与传播记忆点。
2. **atmosphere bible**：记录核心场景的感官锚点与可复用氛围细节。
3. **inner grammar card**：记录角色在压力、撒谎、心动、受伤时的语言与思维模式。

它们不一定都进入硬性的 state contract，但应当成为 Director / Writer 的稳定输入。

---

## 6. Chapter Director：章节导演层的必要性

Chapter Director 是当前架构最值得新增或强化的一层。

它不是 planner，也不是 writer，而是一个 **representation translator**：

- Planner 输出的是“剧本语言”：谁做了什么、冲突是什么、信息如何推进。
- Director 输出的是“小说语言”：哪里慢写、哪里留白、哪里误判、哪里用环境承载情绪。

### 6.1 Chapter Director 的核心输出建议

- `chapter_experience_goal`
- `scene_weight_map`
- `prose_tactics`
- `forbidden_moves`
- `rhythm_plan`
- `transition_requirements`

### 6.2 它直接解决的问题

- 剧本感
- 信息直给
- Scene 平铺直叙
- 段落缺乏缓急变化
- 章节缺少黏合与余味

---

## 7. 章节级文本质量控制：不要直接问“好不好”

章节质量很难完全数值化，但可以拆成**半结构化指标**。与其让 critic 判断“这段是不是好”，不如让它检查“是否满足必要的小说化结构条件”。

### 7.1 沉浸指标（Immersion）

检查：

- 是否有环境锚点
- 是否有身体感受
- 是否有稳定 POV

### 7.2 表达密度（Prose Density）

检查：

- 非摘要句比例是否足够
- 描写 vs 信息比例是否失衡
- 情绪是否被展示，而不只是被命名

### 7.3 节奏变化（Rhythm）

检查：

- 段落长度是否过于单一
- 是否一直对话 / 一直动作 / 一直摘要
- 是否存在主动慢写与呼吸段

### 7.4 章节黏合（Chapter Cohesion）

检查：

- Scene 与 Scene 是否粘住
- 是否有过渡段 / 余波段 / 进入段
- 情绪是否连续传递
- 章节是否形成波形而不是片段堆叠

---

## 8. Writer 生成机制应从“一次完成”改为“双阶段或三阶段”

当前长篇写作中最常见的失真机制是：

```text
scene -> 一次生成 -> 完成
```

这种模式天然会优先满足“功能完成”，而不是“小说感完成”。

更推荐的机制是：

```text
scene -> skeleton -> expansion -> polish
```

### 8.1 Skeleton 阶段

负责：

- 事件顺序
- 冲突点
- 信息边界
- 误判点
- 收尾钩子

### 8.2 Expansion 阶段

负责：

- 环境锚点
- 动作细节
- 对话间隙
- 身体感受
- 情绪渗透
- 节奏快慢变化

### 8.3 Polish 阶段（可选）

负责：

- 去重复
- 调节句式
- 统一语气
- 降低 AI 味

---

## 9. 资源管理器思路仍然成立，但应与章节控制层分工

系统层仍然可以采用“叙事资源管理器”的设计，尤其适用于强系统依赖题材。可维护的对象包括：

- `suspense_budget`
- `reader_knowledge_gap`
- `foreshadow_debt`
- `mystery_exposure_risk`
- `trust_level`
- `relationship_tension`
- `emotion_pressure`
- `agency_balance`
- `payoff_density`

建议把每一章视为一次“状态推进 + 资源结算回合”，但不要指望这些资源直接解决章节内的文学性问题。

它们更适合回答：

- 本章推进了什么
- 透支了什么
- 漏掉了什么
- 是否该触发重规划

而章节层则回答：

- 这一章如何避免写成执行记录
- 如何让 reader experience 成为显式控制目标

---

## 9.1 一个更实操的工作分层

结合实操反馈，可以把文档生产和维护职责再细分为：

- **Intake / Experience Brief**：负责收集卷级、章级体验目标。
- **Canon / Atmosphere Bible**：负责维护长期稳定的世界与场景感官锚点。
- **Character Inner Grammar**：负责固定主要角色的内心回路与语气习惯。
- **Arc / Chapter Emotion Curve**：负责把体验目标下沉到章级起伏设计。
- **Chapter Director**：负责把这些输入翻译成可执行的 prose tactics。

这样，系统层与章节层之间就不再是“Planner 直接把任务丢给 Writer”，而是多了一层稳定的表达材料供应。

---

## 10. 一个务实的 v0.2 / v0.3 路线

### v0.2：从“能跑”升级到“像小说”

优先做两件事：

1. **加入 `chapter_director`（或升级 `prose_director`）**
2. **把 `writer` 改成 `skeleton -> expansion` 双阶段**

这两步最直接解决：

- 剧本感
- 摘要感
- 段落偏空
- Scene 拼接感

### v0.3：把章节级 critic 做成熟

在已有 structure critic 之外，补充：

- `scene_prose_critic`
- `chapter_cohesion_critic`
- `immersion / density / rhythm` 面板
- 自动补过桥段 / 呼吸段 / 余波段

---

## 11. 建议纳入仓库文档体系的原因

这个 idea 文档适合作为仓库中现有架构文档的补充，因为它回答了当前 v0.2 设计背后一个尚未完全显式化的问题：

> **系统层控制与章节层控制不是同一个问题域，必须拆层设计。**

与现有文档的关系建议如下：

- `docs/v0.2-architecture.md`：保留执行流、状态机、角色分工。
- `docs/intake-and-state-contract.md`：保留前台准入与状态契约。
- **本文件**：补足“为什么需要 Chapter Director / 双阶段 Writer / 章节质量控制面板”的设计理由与抽象层次。

---

## 12. 一句话总结

> **Narrative Runtime 负责让小说系统持续运转，Chapter Quality Control 负责让章节看起来像小说。**

两者结合，才构成一个真正可扩展的多 Agent 小说生产系统。
